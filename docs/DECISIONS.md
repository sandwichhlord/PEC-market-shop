P11 — State machine extended: ADMIN may move PLACED_PAID / PREPARING / READY_FOR_PICKUP / COMPLETED → REFUNDED (`ADMIN_FORCE_REFUND_FROM`). Needed because a rejected refund escalates while the order resumes (P02/P09), so an admin's full force refund of an escalated dispute starts from a kitchen status. RESOLVED stays terminal: a full refund there only changes paymentStatus.
P11 — Admin dispute actions (`POST /api/admin/disputes/:id`): `refund` (chosen unrefunded items or `wholeOrder`, note required) and `resolve` (note required). Allowed on OPEN and ESCALATED disputes; anything else 409 DISPUTE_CLOSED (so a repeated force refund is a 409, never a second refund — claim-then-refund with idempotency key `admin-refund-<complaintId>`, un-claimed on provider failure → 502).
P11 — Order outcome of an admin action: OPEN refund request → full: REFUNDED, partial: previous status, resolve: previous status + complaint REJECTED. OPEN complaint → full: REFUNDED, partial or resolve: RESOLVED. ESCALATED → full: REFUNDED, partial/resolve: status unchanged (payment fields, items, notifications and an `order:status` push with from = to so open pages refresh). An ESCALATED dispute cannot be acted on while the order has another OPEN dispute (409 ORDER_IN_DISPUTE).
P11 — Admin dispute decisions notify both the customer and the shop owner (`changeStatus` gained `shopMessage`).
P11 — Account actions: warn (message 5–500 chars → WARNED + ACCOUNT notification), suspend, reinstate (→ ACTIVE, warning cleared). Repeats are 200 `{ changed: false }`; warning a suspended account is 409 (reinstate first); admin accounts are 403 ADMIN_ACCOUNT. Suspension also closes the user's open sockets; the next API request or page load logs them out (existing P03 guards / layouts).
P11 — Reports: a shop reports the customer of one of its paid orders (unpaid / other shops' orders 404); one OPEN report per order (409 ALREADY_REPORTED). Every admin gets a REPORT notification and a `report:changed` push. Report actions: warn / suspend / reinstate → ACTIONED (allowed again on an actioned report, e.g. reinstating later), dismiss → DISMISSED (only from OPEN; repeat is a no-op). Optional admin note stored on the report; the customer is never told which shop reported them.
P11 — Suspending a shop owner is done from the Users or Shops list (same account action); their shop disappears from browsing (P04 rule).
P11 — Admin lists: disputes default to "Needs action" (OPEN + ESCALATED, escalated first, oldest first) with status tabs plus shop/type filters as plain GET forms; reports default to OPEN; users search name/email/phone with role/status filters; all capped at 200 rows. "Paid orders today" now counts by IST midnight.
P12 — Login rate limit (`src/server/auth/rate-limit.ts`, in-memory, one process): failed logins counted in a 15-min fixed window per account+IP (5), per account across IPs (20) and per IP across accounts (30); a locked key gets 429 TOO_MANY_ATTEMPTS + `Retry-After` even with the right password. Only INVALID_CREDENTIALS counts (wrong portal / suspended don't); a successful login clears that account's counters. Keying the tight limit on account+IP means a stranger can't lock the owner out with 5 bad guesses.
